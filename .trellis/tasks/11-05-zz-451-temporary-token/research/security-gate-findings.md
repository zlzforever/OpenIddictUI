# Temporary token security gate findings

The tests use isolated certificates and an in-memory backchannel for actual discovery/JWKS. Run them with `dotnet test tests/OpenIddictUI.Tests/OpenIddictUI.Tests.csproj --filter FullyQualifiedName~TemporaryToken`. The sample API test uses its real strict issuer/audience settings; only its metadata backchannel is redirected to the isolated issuer. No real credentials are used.

## Results and limitations

- A token signed with the isolated server's configured signing credentials is accepted by both local OpenIddict validation and the actual DemoController/JWT Bearer pipeline. The latter obtains the certificate from discovery/JWKS. Invalid issuer, JWT type, signature, lifetime, audience and scope are tested. The repository's sample API now configures issuer, audience, type and zero clock skew validation; this does not establish the configuration of any deployed API.
- Production-pipeline issuer regression tests use `CreateWebApplication` and actual discovery/JWKS responses, with only the HTTP backchannel redirected to the isolated STS. Root and path issuers are tested with a no-trailing-slash Authority. Root discovery previously advertised a different issuer from the signed JWT; discovery now advertises the OpenIddict issuer's `AbsoluteUri`, and the sample API compares token issuer exactly to the canonical configured issuer. The test source is signed using the server's configured key, rather than issued through a full login flow.
- The isolated experiments and the actual temporary-token controller rebuild JSON only after authenticating the same bearer string. Re-signed object, nested array, numeric, boolean, Unicode and role values compare equal using JSON deep equality. JWT metadata and marker differ. Duplicate top-level, escaped-equivalent, and nested property names are rejected. The implementation uses the actual configured scope and audience policy rather than the experiments' hard-coded values.
- A real token from the OpenIddict server token endpoint contains `oi_au_id` when the test principal carries an authorization ID. Local validation and the API accept it, but the conservative proof-of-concept refuses to reissue it. This experiment uses degraded mode, so it does not model token database entries or revocation. It does not prove compatibility for the deployed server, whose token storage is enabled.
- A second non-degraded server uses isolated in-memory SQLite, a real permanent authorization, and enables token-entry and authorization-entry validation. A genuine access token includes `oi_tkn_id`, distinct from `jti`, and `oi_au_id`. A re-signed JWT that reuses the old ID is accepted as the old entry; a JWT without token ID is also accepted. After revoking the source entry, source and copied-ID JWT are rejected but the no-ID JWT still authenticates. After revoking the real authorization, a different unrevoked source token is rejected, but the no-ID JWT **still authenticates even though it retains `oi_au_id`**. Local OpenIddict authorization validation resolves the association from the stored token entry, not the payload alone. An isolated new token entry linked to the authorization makes a freshly signed token pass and then fail when that authorization is revoked; it survives the old token's revocation. This shows the semantics of both approaches, not a production decision to create database entries.
- The stock validation configuration accepted a token with future `nbf` during the earlier experiment. `Program.CreateWebApplication` now post-configures OpenIddict validation to validate lifetime with zero clock skew; production-pipeline regression tests exercise this configuration. This describes the repository configuration, not the state of any deployment.

## OpenIddict 7.7 protocol observations

Inspected upstream tagged source: `OpenIddict.Server/OpenIddictServerHandlers.cs` (`PrepareAccessTokenPrincipal`), `OpenIddict.Server/OpenIddictServerHandlers.Protection.cs` (`CreateTokenEntry`, `AttachTokenSubject`, `AttachTokenMetadata`, `RestoreTokenEntryProperties`), `OpenIddict.Validation/OpenIddictValidationHandlers.Protection.cs`, and `OpenIddict.Abstractions/OpenIddictConstants.cs` at https://github.com/openiddict/openiddict-core/tree/7.7.0/src .

- `oi_` is the reserved private claims prefix. `oi_au_id` identifies an authorization, `oi_tkn_id` a database token entry, and `oi_cl_dstn` stores claim destinations for non-access tokens. The server's access-token principal creation intentionally preserves authorization ID and excludes an inherited token ID; token-entry creation may then set a *new* token ID. `jti` is separately generated and is not the database token ID. Scope, audience, creation/expiration and token type are mapped to public claims/header; presenter and authorization ID can remain private.
- Copying an old token ID into a new token misrepresents the backing entry; keeping only an authorization ID does not make OpenIddict enforce authorization revocation. The implementation rejects unknown/malformed private state and proof-of-possession (`cnf`), retains supported presenter state, and deliberately removes the old token and authorization IDs. The SQLite integration test calls the actual controller with an authenticated, authorization-linked source and verifies that the output is accepted but remains valid when the original token and authorization are revoked. This limitation is explicit in the approved plan and documentation. A separately created entry also preserves the association in the SQLite experiment, but is not used by the implementation.
- The app currently configures `UseLocalServer()` but does not explicitly enable token-entry or authorization-entry validation. This is not evidence that every deployment or external recipient shares that choice. Do not represent a separately signed JWT as instantly revocable.

## Scope reduction: implemented fail-closed policy

For each destination audience, an administrator-managed allowlist defines permitted scopes and `IndependentClaims` names. All source claims must be classified: metadata is handled under protocol rules, and each business claim name must appear in the destination's `IndependentClaims`. Unknown business claim names or missing policy deny signing rather than removing or rewriting a claim. The implementation does not validate each claim value's schema or semantics; the receiving service's administrator must review and attest that all accepted values are scope-independent, including roles, tenant/resource selectors and nested permissions. Reject a selected scope unless every selected scope maps to at least one allowed audience also in the source; resulting audiences must be a source subset. The empty default whitelist disables issuance. Configuration of claim names alone is not a substitute for the destination owner's semantic review.

`TemporaryTokenScopePolicyGateTests` exercises the scope subset, source-audience intersection, case/duplicate/empty rejection and claim classification per each selected audience. The actual controller test additionally covers multiple scopes and audiences and rejects a JWT if any output scope/audience pair was not configured, because every audience sees every scope. Before enabling a destination, its service owner must attest the actual claim contract, enforce the read-only marker on every shared-audience service and validate issuer/signature/audience/scope/time. Repository inspection alone cannot establish those external facts. Unknown claims may make some otherwise valid tokens unshareable; that is explicitly preferable to silent privilege expansion.
